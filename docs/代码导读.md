# 从文件结构读懂 C++ 版本

## 1. 先看四个任务目录

`task1/` 是概念设计，`task2/` 是实际表结构，`task3/` 是导入和准确性查询，`task4/` 是可运行的应用。根目录的 `run.sh` 负责把程序和数据库启动起来，`Makefile` 负责将 C++ 源码编译成 build/metro。

`data/` 保存官方 CSV，`task4/data/` 保存票价补充数据。`build/` 是编译产物，`.runtime/` 是本机 PostgreSQL 实际数据库文件。这两类目录在打包时排除。

## 2. 推荐的阅读顺序

### 第一步，main.cpp 与启动命令

先打开 `task4/src/main.cpp`。它读取运行参数，生成 Config，然后按命令选择导入、网页、命令行或图导出。Config 包含项目根目录、数据库连接信息、监听地址及端口。

执行 `bash run.sh` 时，脚本先调用 make 编译，再调用 `build-import` 生成 SQL，启动项目 PostgreSQL，执行 `init`，最后启动 `serve`。已有 DATABASE_URL 时使用指定数据库。

### 第二步，app.hpp 与 C++ 类型

`task4/include/app.hpp` 是公共声明。Json 是 nlohmann::json 的别名。Params 保存 SQL 参数，`std::optional<std::string>` 的空值代表 SQL NULL。Error 除错误文字外还携带 HTTP 状态码。

Service 的公开方法对应业务动作。HTTP 和 CLI 都调用这些方法。头文件只声明接口，具体实现分布在 src/ 各个 cpp 文件。

### 第三步，db.cpp 与资源管理

Db 构造函数用 PQconnectdbParams 连接 PostgreSQL，并使用 UTF-8。run 调用 PQexecParams，将 SQL 和参数分开发给数据库，避免把用户输入直接拼进 SQL。

Db::run 根据字段类型，把结果转换成 JSON 数字、字符串、布尔值、空值或 JSON 数组。HTTP 再将 JSON 文本返回浏览器。

Db::begin 开启事务。写操作取得事务级 advisory lock，避免两个操作同时修改同一份站序。Db::commit 提交。Db 对象析构时会回滚尚未完成的事务并关闭连接，这是一种 RAII 资源管理方式。

阅读时重点跟踪一个 Db 对象的生命周期，它决定一次操作何时成功、失败时如何恢复。

### 第四步，schema.sql 与 import.cpp

先读 task2/schema.sql 的七张表。station 与 metro_line 通过 line_stop 形成多对多关系，出口与地标通过 exit_landmark 形成多对多关系。

再读 import.cpp。它读取 CSV，识别同一个实体站点，分配稳定 ID，处理空值、坐标和梨园歧义，最后生成完整的 task3/import.sql。该 SQL 可以单独在 DataGrip 执行，运行现场导入时无需程序再读取 CSV。

### 第五步，validation.cpp 与输入检查

HTTP 的 JSON 输入进入业务方法后，先检查允许的字段、必填值、名称长度、坐标范围、状态值、年份及时间格式。PATCH 只修改提供的字段，所以新增与修改采用不同的必填规则。

输入校验负责让错误尽早可读地暴露。PostgreSQL 的主键、外键、唯一性等约束继续提供数据库级保证。

### 第六步，service.cpp 与一次新增站点

从 save_station 开始。它先校验输入，然后开启写事务，将行政区名称转为 district_id，写入 station，提交事务，返回新增记录。

同样的方法同时服务网页和命令行。新增逻辑集中在这里，界面层只负责接收与展示。

再看 insert_stops。它检查批次重复、站点存在性和线路已有站点；延迟站序唯一约束；将后续站点的 position 加上插入数量；按输入顺序插入；最后提交。任一步失败，Db 析构回滚整批修改。

### 第七步，http.cpp 与浏览器请求

http.cpp 使用 cpp-httplib 注册 GET、POST、PATCH、DELETE 路由。例如 POST /api/stations 会解析 JSON，然后调用 service.save_station，并返回状态码 201。

浏览器访问 `/` 时取得 HTML，访问 `/assets/` 取得 JavaScript、CSS 和字体。app.js 的 api 函数通过 fetch 发送请求，其他函数负责表单、表格、弹窗和线网绘制。

可以沿这条链追踪一次新增动作。

```text
index.html 的表单
→ app.js 的 submitEditor
→ POST /api/stations
→ http.cpp
→ Service::save_station
→ Db::run 与 PostgreSQL
→ JSON 返回
→ app.js 刷新表格
```

### 第八步，routes.cpp 与路径搜索

load_network 将线路中相邻的站点连接成双向图。先识别相邻站，再按运营状态过滤，防止跨过中间在建站。

shortest 使用 Dijkstra。状态由“站点 ID、当前线路 ID”组成，因此到达同一个站但乘坐不同线路，会作为不同状态参与换乘成本计算。

站数优先时，优先比较站数，再比较换乘数。换乘优先时，顺序反过来。previous 保存每个状态来自哪里，搜索结束后倒推完整路线，再合并为线路区段。

地标查询把全部可用出口站点作为候选起终点，进行多源搜索。fare 先查公布矩阵，再在资料不足时提供清楚标记的估算。

### 第九步，tests/integration.cpp

测试程序创建随机的专用测试库，逐项导入、检查，完成后删除。它核对全部站点与出口原始记录，检查 CRUD、回滚、并发插站、路径及 HTTP。

源码中的 check 类似断言，rejects 检查某操作应当报错。路径结果还与一个独立 BFS 的最少站数结果比较。

## 3. 建议的第一次修改练习

1. 在网页新增一个站点，观察返回的 station_id。
2. 在 service.cpp 的 save_station 中找到 INSERT，与表结构逐列对应。
3. 查看 db.cpp 如何将参数传给 PQexecParams。
4. 找到 app.js 的 submitEditor，观察它提交了哪些 JSON 字段。
5. 给新增站点加入一条测试线路，再在线路中间插入第二个站点，观察 position 的变化。

先能顺着一次请求说清楚每层干了什么，再读路径算法的优先队列和 C++ 所有权细节。
